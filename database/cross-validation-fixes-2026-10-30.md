# DealVue 교차검증 후 수정 — 2026-10-30

## 적용 범위

사용자가 승인한 다섯 항목을 수정했다. 아바타 이미지·디자인은 바꾸지 않았으며 웹 배포, 커밋, 푸시는 하지 않았다. 운영 Supabase에는 기존 예약 함수의 할인 시간 판정만 적용했다. 테이블·권한·가격·수량·원본 시간표·기존 예약은 변경하지 않았다.

## 할인 및 예약 시간

사용자가 명확히 정정한 규칙은 **할인 방문 시간에 예약을 시작하면 할인**이다. 판정 구간은 시작 포함, 종료 제외 `[start,end)`다. 시술 종료가 할인 시간 이후여도 가능하며, 매장 영업시간 및 담당자 근무시간에는 시술 전체가 들어와야 한다. 담당자 충돌 검사·점유·취소 시 해제는 실제 시술 전체 구간을 계속 사용한다.

- `database/consumer-booking.sql`: 신규 설치용 정의 수정.
- `database/consumer-booking-start-window.sql`: 운영 기존 함수의 두 조건만 교체하는 재실행 가능한 패치. 실제 SQL Editor 결과 `start_window_enabled=true`, `full_occupancy_preserved=true` 확인.
- `catalogData.ts`, `booking/visitWindow.ts`: 할인 후보는 영업시간 내 전체 시술이 가능한 시작 후보 가운데 할인 시작 구간에 든 시간만 선택.
- `CheckoutPage.tsx`, `BookingSchedulePicker.tsx`: 특가 진행 중에도 정상가 시간을 선택할 수 있다. 각 시간 버튼에 서버 요금을 표시하고 선택한 행의 종류·금액으로 동의를 받는다. 선택 전 확정 금액은 표시하지 않는다. 수량 소진을 ‘진행 시간 아님’으로 단정하던 문구를 제거했다.
- 확대하려던 원본 할인 시간 변경은 모두 되돌렸다.

### 남은 원본 시간표 충돌 1개

`provided:riobella:service:5` 리오벨라 ‘데이트 맞춤 메이크업’: 할인 시작 19:30, 시술 점유 90분, 영업 종료 20:30. 시작 시간 기준으로 바꿔도 최초 종료가 21:00이므로 영업시간 내 할인 예약이 없다. 이 시술의 이른 시간 정상가 예약은 가능하다. 영업시간이나 할인 시작 시간을 임의로 변경하지 않았다. 나머지 74개 템플릿은 원본 영업·휴무·시술 시간을 그대로 사용한 격리 DB 검사에서 할인 시작 후보가 존재했다. 담당자 예약 현황에 따른 실제 잔여 자리 보장은 별개다.

## 계정 분리

- `accountScope.ts`: 계정 ID에 따라 Zustand 저장 키를 분리하고 계정 전환 시 메모리를 초기화한 뒤 해당 계정 데이터를 불러온다.
- `ledger.ts`: IndexedDB 키도 계정별로 분리한다. 이전 계정에서 시작된 저장은 이전 키에만 반영하며, 지연 응답·낙관적 처리·다른 탭 알림이 새 계정 화면을 덮어쓰지 못하게 한다.
- 포인트·출석·운세 보상·룰렛·의상 및 장신구 소유·외형·저장 코디·로컬 찜·레거시 쿠폰/예약 저장소에 적용했다. 서버 예약·쿠폰·커뮤니티의 기존 계정 구분은 유지했다.
- **기존 공용 기기 데이터는 소유 계정을 알 수 없어 게스트 저장소에 보존한다. 임의의 로그인 계정으로 잔액이나 소유 아이템을 복사하지 않는다.** 따라서 로그인 계정의 초기 로컬 잔액/옷장이 기존 공용 화면과 다를 수 있다. 원본 데이터는 삭제하지 않았다.
- 이 변경은 같은 브라우저 내 계정 분리다. 로컬 포인트·옷장이 다른 휴대폰까지 동기화되는 것은 아니다. 서버 공유 예약은 별개로 유지된다.

## 로그아웃

`requestLogout()`에서 `auth.signOut({scope:'local'})`를 명시한다. 기본 global 로그아웃으로 다른 기기 세션까지 종료하던 호출을 바꿨다. Supabase 공식 문서: https://supabase.com/docs/reference/javascript/auth-signout

## 예약 응답 유실

- 요청 전 계정·상품별 sessionStorage에 요청 ID와 동의한 일정·담당자·요금을 저장한다.
- 네트워크 오류나 게이트웨이 장애는 ‘예약 실패’로 단정하지 않고 접수 확인 상태로 남긴다.
- ‘예약 결과 확인’은 최초와 동일한 요청을 서버에 다시 전송한다. 기존 서버 멱등성 검사가 이미 접수된 예약 ID를 반환하므로 본인 예약으로 시간이 막혔어도 확인할 수 있다.
- 페이지 새로고침 후에도 보류 요청을 복구한다. 확인 중에는 입력을 잠그고 원래 일정·금액을 표시한다. 서버가 명확히 거절한 경우에만 보류 요청을 지우고 다시 선택하게 한다.
- 탭을 완전히 닫으면 sessionStorage 보류 정보는 사라진다. 서버 예약은 남고 예약내역에서 확인할 수 있다.

## 검증 및 한계

- `check-consumer-booking-db.mjs`: 네트워크 없는 PGlite DB. 실제 75개 템플릿 검사, 패치 재실행, 시작·종료 경계, 할인 종료 이후 시술 및 일정 변경, 전체 점유·인접 예약·다른 담당자·취소 해제·멱등성·변경 실패 롤백·패키지 전체 롤백·기존 읽기 최적화 결과 일치 검사.
- `check-account-isolation.mjs`: 실제 Zustand 저장소와 임시 fake-indexeddb. A/B/게스트 전환, 출석 중복, 포인트·구입 의상·외형·코디·룰렛·찜 분리, 계정 전환 중 쓰기/지연 읽기 검사. 운영 브라우저 데이터에는 접근하지 않는다.
- `check-booking-response.mjs`: 실제 API 래퍼 + 전송 모의 객체. 접수 후 응답 유실, 새로고침에 해당하는 보류 요청 재조회, 동일 요청 복구, 다른 계정 격리, 명확한 DB 거절/게이트웨이 불확실성 구분, local 로그아웃 인자 검사.
- `check-shared-query.mjs`, `check-catalog-traffic.mjs`: 기존 요청 공유·백오프·숨긴 탭 정지·메타데이터 캐시·자정 만료 유지.
- Safari 실제 로그인된 로컬 모바일 화면(390×844)에서 벨루니크 10월 31일 13:30 선택 시 특가 35,000원, 14:00 선택 시 정상가 50,000원 및 요금 전환 확인. 13:30 시술은 60분이므로 할인 종료 13:40을 지나 끝난다. 운영 함수 변경과 실제 UI의 일치를 확인했다.

- 동시 접속 50/100/200명 실제 부하 테스트는 수행하지 않았다. 처리 인원을 보장하지 않는다. 이번 수정에 새 폴링/외부 서비스/런타임 라이브러리는 추가하지 않았다.
