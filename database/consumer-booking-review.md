# 예약 서버 공유 전환 및 재점검 결과

검증일: 2026-10-29 (한국 시간)

## 결론

신규 예약을 기기 저장에서 Supabase 공통 예약으로 전환했습니다. 홈 타임딜, 매장 시술, 딜 상세, 딜키트가 사용하는 Checkout에서 서버 RPC로 생성하며, 예약 상세의 변경·취소도 서버에서 처리합니다. 승인받은 `consumer-booking.sql`을 운영 Supabase에 적용했고, 서로 다른 가상 계정의 실제 HTTP 동시 요청과 Safari 모바일 화면에서 재검증했습니다. 웹 배포·커밋·푸시는 하지 않았습니다.

## 수정 결과

| 이전 문제 | 수정 내용 | 검증 |
|---|---|---|
| 다른 휴대폰 예약과 자리 공유 안 됨 | 기존 reservations에 저장, 담당자 ID와 전체 시작~종료 구간 검사 | 실제 두 계정 동시 요청 중 한 건만 성공 |
| 긴 시술 중간 시간에 다른 사람 예약 가능 | DB 시간 구간 중복 금지 제약과 서버 조회 사용 | 180분 시술과 겹치는 시작 시간 모두 예약 불가 |
| 안내용 70분을 실제 점유 90분 대신 사용 | 단일 시술 점유는 services.duration_minutes 사용 | 격리 DB의 안내 170분/점유 180분 사례에서 180분 점유 확인 |
| 변경 시 충돌, 실패 후 원래 자리 유실 가능 | 동일 트랜잭션에서 검사·변경, 이전 시작 시각으로 동시 수정 검사 | 충돌 변경 거절 및 원래 예약 유지, 실제 변경 성공 |
| 취소 후 자리 복구 불명확 | 서버 취소로 점유 및 딜 수량 해제, 반복 취소 허용 | 실제 취소 후 다른 계정에서 해당 시간 예약 가능 |
| 재시도 중복 생성 가능 | 계정+요청 ID와 요청 내용 저장, 같은 요청은 같은 예약 반환 | 실제 재전송 동일 ID, 격리 DB에서 다른 내용의 키 재사용 거절 |
| 패키지 일부만 예약/취소 | 전체 방문을 한 트랜잭션으로 생성·취소 | 실제 두 매장 예약·총액 90,000원·전체 취소, 격리 DB에서 두 번째 방문 실패 시 전체 롤백 |
| 변경 기본 날짜가 오늘로 선택됨 | 원래 예약일·시간을 기본 선택하고 같은 시간은 저장 비활성화 | Safari에서 10월 30일 10:30 선택 상태 확인 |
| 예약 시 결제·환불 안내 혼재 | 방문 시 매장 결제, 예약 시 결제 없음으로 통일 | Checkout·상세·취소·매장 상세·상담 문구 정리 |
| 쿠폰 안내가 예약 시 사용으로 표시 | 홈·쿠폰 정의·상담을 결제 시 사용으로 변경 | 실제 홈과 쿠폰함 문구 확인 |
| 친구 초대 보상이 구현 없이 확정 안내 | 보상 확정 문구를 정보 공유 안내로 변경 | 마이페이지 표시 확인 |

시술 종료와 다음 예약 시작이 정확히 같은 경우는 허용합니다(`[시작, 종료)`). 담당자가 다르면 같은 시간에 예약할 수 있습니다. ‘매장 배정’은 서버가 가능한 담당자를 선택합니다. 남은 수량과 시간표는 10초 주기 및 창 복귀/예약 변경 시 갱신하고, 마지막 확정은 항상 서버가 검사합니다.

## 타임딜 할인 기준

- 서버가 판매 순환 회차, 잔여 수량, 실제 방문 시간대, 시술 종료 시각을 확인합니다.
- 14:00~18:00 시간대에 180분 시술이면 14:00 / 14:30 / 15:00 시작만 할인 대상입니다. 18시 이후까지 시술이 이어지는 시작 시각은 할인되지 않습니다.
- 딜이 마감되거나 소진되면 정상가로 전환하며, 기존에 동의한 금액과 다르면 예약 제출을 거절하고 다시 확인하도록 합니다. 브라우저에서 할인 종류·금액을 바꿔 보내도 서버가 재계산합니다.
- 현재 정책은 **판매 중에 향후 2주 안의 동일 방문 시간대를 예약할 수 있는 방식**입니다. ‘판매 당일 방문에만 할인’으로 정책을 추가 변경하지는 않았습니다.
- 이미 할인 예약을 완료한 뒤 판매가 마감되었다는 이유만으로 금액을 올리지는 않습니다. 일정 변경은 할인 방문 시간 안에서만 허용합니다.

## 실제 검증 기록

### 운영 서버

개인정보 없는 가상 계정 2개를 사용했습니다. 기존 사용자 계정의 예약은 변경하지 않았습니다.

- 서로 다른 계정으로 동일 담당자·시간에 동시에 요청: 한 건 성공, 한 건 거절.
- 180분 예약 구간과 겹치는 모든 후보: 다른 계정에서 예약 불가.
- 같은 시각의 다른 담당자: 예약 가능.
- 상대 계정의 예약 조회: 빈 결과. 상대 계정 취소 및 브라우저 직접 가격 수정: 거절.
- 실제 일정 변경 성공, 취소 성공, 취소 후 시간 복구 확인.
- 같은 요청 ID 재전송: 동일 예약 번호 반환.
- 두 매장 패키지: 방문 2건과 총액 일치, 재전송으로 방문 수 증가 없음, 취소 시 모두 취소.
- 테스트로 만든 예약 번호 1~6은 모두 취소했습니다. 테스트 계정에 활성 예약이 남지 않은 것을 마지막 API 조회로 확인했습니다.

### Safari 화면, 390×844

기존 localhost:5173 계정에 영향을 주지 않도록 별도 localhost:5174에서 같은 코드를 실행했습니다. 검증 후 임시 서버와 로컬 테스트 자격증명 파일은 정리했습니다.

- 실제 이메일 로그인 → 서버 예약 목록·상세 조회.
- 일정 변경 창: 기존 날짜 10월 30일과 10:30이 기본 선택, 변경하지 않으면 저장 비활성화.
- 화면에서 11:00 변경 → 상세에 11:00~14:00 반영 → 취소 완료 표시.
- Checkout에서 담당자·시간 선택 → 예약 버튼 → `/booking/complete/6`의 ‘예약이 완료되었습니다’, 담당자·일시·방문 시 결제 금액 확인 → 상세에서 취소.
- 홈 타임딜 5개 및 쿠폰의 ‘결제 시 사용 가능’ 표시 확인.

### 격리 PostgreSQL

`PGLITE_MODULE_PATH=/임시설치경로/@electric-sql/pglite/dist/index.js node scripts/check-consumer-booking-db.mjs`

마이그레이션 재실행, 담당자 전체 구간 충돌, 경계 시각, 계정 격리, 직접 쓰기 제한, 내부 함수 호출 제한, 재시도, 동시 수정 감지, 변경 실패 원상 유지, 패키지 롤백, 할인 시간·수량·가격 위조 거절, 익명 잔여 수량 조회에 예약 정보가 포함되지 않는 것을 통과했습니다.

TypeScript 포함 build, lint, diff 공백 검사도 수행했습니다. 기존 큰 번들 경고는 남아 있습니다.

## 이전 데이터와 남은 범위

- 이전 브라우저 장부 예약을 서버로 무조건 복사하지 않았습니다. 이미 담당자나 시간이 겹칠 수 있고 당시 담당자 ID가 저장되지 않았기 때문입니다. 이전 내역은 보존하고, 향후 방문 예정인 이전 예약은 다시 예약할 수 있도록 구분합니다. 기존 기기 예약으로 서버 점유가 생겼다고 표시하지 않습니다.
- 실제 휴대폰 하드웨어 두 대 및 50/100/200명 부하 시험은 수행하지 않았습니다. 두 독립 계정의 실제 동시 HTTP 요청을 검증한 것이며, 특정 동시 접속 인원을 보장하는 결과가 아닙니다.
- Google/Kakao 인증 전체 재시험, 리뷰·포인트의 서버 이관, 전 메뉴의 모든 조합 검증은 이번 예약 전환 범위에 포함하지 않았습니다.
- 패키지 일정 변경은 기존처럼 취소 후 재예약 방식입니다. 서로 다른 매장 간 이동시간 30분 정책도 유지했습니다.
- 운영 DB는 적용되었지만 공개 웹사이트 프런트엔드는 아직 배포하지 않았습니다. 공개 사이트도 새 서버 예약 경로를 사용하려면 후속 웹 배포가 필요합니다.
