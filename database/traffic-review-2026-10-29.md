# 전시 트래픽 검토 — 2026-10-29

보안·결제를 제외하고 현재 작업 트리의 요청 구조와 정적 파일을 검토했다. 기능 충돌 테스트 통과와 동시 접속 성능 보장은 별개다. 운영 서버에 50~200명 부하를 발생시키는 테스트는 수행하지 않았다. 최초 검토 단계에서는 웹 배포 및 기능 코드를 변경하지 않았다. 후속 변경은 다음 절에 기록한다.

## 같은 날 후속 최적화 결과

아래 최초 검토의 문제 목록은 변경 전 상태다. 사용자 요청에 따라 다음을 구현했다. 운영 DB의 조회 함수 두 개는 적용했으며 웹 배포는 하지 않았다.

- 전체 카탈로그를 매번 조회하던 경로를 메타데이터 10분 캐시 + 실시간 수량 갱신으로 분리했다. 서울 자정에는 캐시가 만료되지 않았어도 날짜 후보를 다시 만든다. 20개 동시 호출도 한 번으로 합쳐지며, 테스트에서 최초 5개/이후 갱신 1개 요청을 확인했다. 정기 갱신 요청 수가 캐시 유효 기간에 **80% 감소**한다. 최초 로딩과 10분마다 재조회는 별도다.
- 카탈로그·시간 조회·계정별 예약 내역을 공유 조회로 통일했다. 같은 키의 요청은 겹치지 않고, 응답이 끝난 후 다음 조회를 예약한다. 화면 비활성 시 중단하며 복귀 시 오래된 정보를 갱신한다. 예약 변경 이벤트는 즉시 무효화하고, 조회 도중 이벤트가 와도 완료 뒤 한 번 더 갱신한다. 실패 시 간격을 늘리고 각 기기의 폴링 시간을 분산한다.
- 빈 시간 캐시 키에는 계정/시술/날짜/담당자/변경 대상 예약이 포함된다. 계정별 본인 예약 충돌 조건이 섞이지 않는다.
- 예약 내역은 10초에서 30초 주기로 조정했다. 예약 생성·변경·취소 후에는 즉시 갱신한다. 매번 원격 인증 요청을 보내는 대신 현재 로컬 세션을 확인하고, DB는 기존 본인 예약 정책을 계속 적용한다. 필요한 열과 매장 이미지 한 개만 가져온다.
- DB 빈 시간 조회는 첫 매장의 영업시간과 시술 길이로 후보 범위를 먼저 제한한다. 휴일은 조기 반환하고, 유효 후보는 기존 계획 검증을 그대로 거친다. 운영 스모크 테스트의 180분 시술은 종전 48개 후보 대신 16개 범위만 검사하며, 유효 시간 반환은 유지됐다.
- DB 수량 조회의 회차 계산을 시술별 대신 매장별로 한 번씩 수행한다. 제공 매장 기준 75개 시술/15개 매장이다.
- 홈 첫 배너 이미지는 우선 로드하고 다른 배너 및 인기 목록 이미지는 지연 로드한다. 이미지 원본·품질·아바타는 변경하지 않았다. 제공 매장 이미지 경로는 이미 `/images/provided/...` 형태로 프론트엔드에 포함돼 있다. 사용자가 업로드하는 커뮤니티 사진 등 기존 Storage 경로는 유지한다.

검증: `check-shared-query.mjs`, `check-catalog-traffic.mjs`, `check-consumer-booking-db.mjs`, lint 및 build 통과. DB 테스트는 이전 48개 시간 후보 방식과 최적화 방식의 전체 결과를 비교하며 패키지/담당자/점유/변경 제외 예약/30분 경계가 아닌 영업시간/짧은 영업일/오늘 날짜/수량 집계가 일치했다. 기존 충돌·변경 실패 롤백·취소·멱등성 회귀 검증도 통과했다. 운영 DB에서는 최적화 정의 존재, 수량 75개, 유효 시간 16개 반환 및 기존 실행 권한 유지를 확인했다. Safari 로컬 화면에서는 홈 배너 이미지/매장별 5개 딜, 예약 진입, 날짜·담당자 변경 후 시간표 갱신을 확인했다. 이번 점검에서는 새 예약을 생성하지 않았다.

남은 한계: 모든 매장의 예약 쓰기를 직렬화하는 잠금은 유지했다. 이는 읽기 폴링과 별개의 경로로, 충돌·패키지 원자성을 유지하기 위해 이번 읽기 최적화와 섞어 변경하지 않았다. 실제 잠금 대기와 50/100/200명 부하는 아직 측정하지 않았으므로 수용량을 보장하지 않는다. 메타데이터 변경은 최대 10분 뒤 반영되지만 확정 시 가격과 점유를 서버에서 다시 검증한다. 최초 전송 이미지 크기는 그대로다.

## 판단

현재 상태를 성능까지 완벽하게 검증했다고 볼 수 없다. 추가 유료 인프라보다 불필요한 반복 조회와 이미지 전송량을 먼저 줄이는 편이 맞다. 50/100/200명 수용 가능 여부는 아래 개선 뒤 격리 환경에서 측정해야 한다.

## 확인된 요청량

`catalog.ts`는 화면에 있는 훅마다 10초 간격으로 `requestConsumerCatalog()` 전체를 다시 실행한다. 제공 매장 데이터가 있는 정상 경로는 템플릿, 수량 RPC, 매장, 시술, 이미지 목록의 **5개 HTTP 요청**이다. 마지막 3개만 병렬이며 앞의 2개는 순차다. 숨겨진 탭은 카탈로그·시간 조회를 건너뛴다.

동일 화면을 계속 열어 두고 카탈로그 훅이 하나인 경우의 코드 기반 계산이다. 이미지·최초 로딩·인증·추가 데이터·포커스 이벤트·사용자 조작은 제외했다. HTTP 요청 수이며 PostgreSQL 연결 수나 처리 가능량이 아니다.

| 화면 | 50명 | 100명 | 200명 |
| --- | ---: | ---: | ---: |
| 홈: 카탈로그 5회/10초 | 25 요청/초 | 50 요청/초 | 100 요청/초 |
| 예약: 카탈로그 5 + 시간 조회 1회/10초 | 30 요청/초 | 60 요청/초 | 120 요청/초 |

각 사용자의 타이머 시작 시점이 겹치면 평균보다 큰 순간 부하가 생긴다. 조회가 10초보다 느려져도 다음 요청을 시작하며, 오래된 응답 무시 처리는 서버에서 진행 중인 이전 쿼리를 취소하지 않는다.

예약 목록 훅은 10초마다 `auth.getUser()`와 예약 목록 조회를 실행한다. 숨겨진 탭도 계속 갱신한다. 예약 상세는 이 조회에 카탈로그와 시간 조회도 더해진다. 목록 조회에는 페이지 제한이 없고 모든 예약 열과 매장 이미지 목록까지 포함한다. 현재 마이페이지 대시보드와 통계는 별도 라우트여서 두 훅이 항상 동시에 실행되는 것은 아니다.

## 우선 개선 대상

1. **전체 카탈로그 반복 조회 — 높음**
   - 파일: `src/features/consumer/catalog.ts`, `catalogData.ts`.
   - 변하지 않는 매장·시술·템플릿·이미지는 공유 캐시로 보관하고, 잔여 수량만 짧은 주기로 갱신한다. 동일 요청 합치기, 진행 중 요청 중복 방지, 실패 시 재시도 간격 증가, 타이머 분산이 필요하다.
   - 5회 중 4회를 매번 반복할 이유가 없다. 최종 예약의 DB 재검증은 그대로 유지해야 한다.
2. **빈 시간 RPC의 반복 계산 — 높음**
   - 파일: `database/consumer-booking.sql`, `useSharedSlots.ts`.
   - 하루 48개 시작 시간을 순회하며 각각 예약 계획·영업시간·사용자 중복·담당자 점유를 검사한다. HTTP 한 번이 가벼운 DB 조회 한 번을 뜻하지 않는다.
   - 영업시간/시술/담당자 데이터를 한 번 읽고 후보를 집합 연산으로 계산하는 방식을 검토한다. 화면의 날짜·담당자가 바뀔 때와 예약 처리 후에는 즉시 갱신하되 중복 요청은 합친다.
   - 수량 RPC도 75개 시술별 상관 서브쿼리와 회차 계산을 사용한다. 현재 인덱스는 있으나 매장별 회차를 한 번 계산하고 집계하는 편이 유리할 수 있다. 실행 계획으로 검증할 사항이다.
3. **모든 매장이 공유하는 예약 잠금 — 중간~높음**
   - 생성·변경·취소와 기존 트리거가 동일한 advisory transaction lock을 사용한다.
   - 충돌 방지를 위해 넣은 현재 구현은 서로 무관한 매장의 예약 쓰기까지 순서대로 처리한다. 오류보다 대기와 타임아웃 위험이다. 실제 잠금 보유 시간은 측정하지 않았다.
   - 매장/사용자 등 필요한 범위로 잠금을 나누려면 패키지·변경의 잠금 순서와 기존 트리거도 함께 수정해야 한다. 잠금만 삭제하면 안 된다. 기존 배타 제약과 동시성 회귀 검증을 유지한다.
4. **이미지 전송량 — 높음**
   - 로컬 `public/images` 총 약 265MiB, 그중 제공 매장 이미지 140개 약 207MiB, 커뮤니티 6개 약 13.6MiB다. 폴더 전체가 첫 화면에서 다운로드되는 것은 아니다.
   - 개별 PNG에 2~3MiB급이 많다. 수정구슬 약 2.53MiB, 커뮤니티 속눈썹 약 2.41MiB, 미용실 약 2.35MiB다.
   - 홈 배너·인기 목록 이미지에는 lazy loading이 없다. 첫 배너는 우선 로드하고 나머지는 지연 로드, 표시 크기별 WebP/AVIF 생성, 썸네일 분리가 필요하다. URL별 브라우저 캐시로 중복 전송을 피할 수 있으므로 DOM 이미지 개수를 그대로 전송 횟수로 계산해서는 안 된다.
   - 예를 들어 실제 방문 전송량이 10MB라면 신규 기기 1,000대는 약 10GB다. 이는 예시이며 현재 페이지 전송량 실측이 아니다. 로컬 `/images`는 Vercel, Supabase Storage URL은 Supabase의 전송량에 각각 반영된다.
5. **예약 내역 갱신 — 중간**
   - 숨긴 화면에서는 중단하고 복귀·변경 이벤트 때 갱신한다. 필요한 열/대표 이미지 한 개만 조회하고 내역이 늘면 페이지를 나눈다. 매 10초 인증 재확인의 필요성도 별도 검토한다.

## 유지할 부분

- 아바타 화면과 무거운 렌더러는 lazy import 경로가 있다. 옷 변경 회전 이미지는 해당 변경에 필요한 그림을 디코딩하고 캐시한다. 모든 의상을 처음부터 받는 구조로 바꾸지 않는다.
- 구형 service worker는 캐시를 제거하고 등록 해제하는 용도이며 전체 `public` 파일을 사전 다운로드하지 않는다.
- 커뮤니티 피드는 RPC에서 30개로 제한된다. 현재 데이터 양에서는 무제한 피드 조회보다 우려가 작다. 댓글은 전체 조회이므로 향후 증가 시 페이지 처리가 필요하다.
- 정합성 검사와 재시도 멱등성은 유지한다. 성능 최적화를 위해 예약 확정 검증을 브라우저로 옮기지 않는다.

## 필요한 실측

격리된 DB와 동일 데이터로 50/100/200명의 읽기 중심 시나리오 및 예약 순간 집중 시나리오를 분리한다. p50/p95/p99 응답시간, 실패율, DB CPU, 잠금 대기, 쿼리 실행계획을 기록한다. 같은 담당자에 대한 경쟁 요청은 성공 한 건, 나머지는 정상 마감 응답인지도 함께 확인한다. 실제 모바일에서 첫 방문 전송량과 이미지/아바타 조작 프레임도 측정한다. 테스트 DB의 사양이 다르면 운영 수용량으로 단정하지 않는다.

## 공식 플랜 참고

- Supabase Free 전송량은 일반 egress 5GB와 cached egress 5GB가 별도다. 하나의 자유로운 10GB 풀로 계산하지 않는다: https://supabase.com/docs/guides/platform/manage-your-usage/egress
- Vercel Hobby Fast Data Transfer는 공식 가이드의 최대 100GB를 참고하되 실제 프로젝트의 잔여 사용량은 대시보드 확인이 필요하다: https://vercel.com/docs/limits/fair-use-guidelines

플랜의 전송량 한도가 남았다는 사실은 DB의 순간 처리 성능을 보장하지 않는다.
